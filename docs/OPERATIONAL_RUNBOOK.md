# Запуск готовых программ

Обновлено 12.10.2026. Это краткий маршрут для рабочих операций, отдельно от офлайн `agent/`. Начинать с существующей программы, а не с нового исполнителя.

## Daktela → перезагрузка AP → оформление заявки

Готовая программа: `daktela_ap_reboot_runner.py`. Launcher `run_daktela_ap_reboot.cmd` вызывает её через Python 3.14 с `--yes`. Python runner также работает LIVE по умолчанию. Для управляемого запуска из Codex предпочтительнее прямой вызов Python: у CMD есть интерактивный `pause`.

Инвентаризация выбранных заявок:

```powershell
py -3.14 daktela_ap_reboot_runner.py --dry-run --keep-open --ticket-id <ID1> --ticket-id <ID2>
```

Рабочий запуск тех же выбранных заявок после устранения применимых блокеров:

```powershell
py -3.14 daktela_ap_reboot_runner.py --yes --keep-open --ticket-id <ID1> --ticket-id <ID2>
```

`<ID1>` / `<ID2>` — placeholders: заменить фактическими ID, не выполнять буквально. Без `--ticket-id` runner берёт найденные числовые заголовки текущей страницы ????????? ??????? Daktela; это не доказательство охвата всей очереди. `--ticket-spec` предназначен для возобновления уже подтверждённой цели, а не для угадывания объекта.

1. Если пользователь выбрал работу через Daktela, выяснить цели в подтверждённой очереди ????????? ??????? Daktela. Проверить смысл заголовков, затем ограничить запуск ID подходящих заявок. Не спрашивать заново отель, разрешение reboot или closure, уже установленные в разговоре.
2. Проверить только применимые известные блокеры ниже. Пока они не устранены, команда LIVE — шаблон, не одобрение небезопасного запуска. Если нужен wrapper, использовать один проверенный и переиспользуемый; не создавать отдельную программу для каждого шага/контроллера.
3. Войти один раз в Daktela/XNet, сохранять браузер до окончания операции. Поддержка `--keep-open` сама по себе не доказана: раньше выход Python завершал driver/browser. Не рассчитывать на этот флаг без проверки жизненного цикла сессии.
4. Выполнить разрешённые перезагрузки через существующий backend. После возможной отправки команды не запускать второй backend до выяснения результата. Блокер одного отеля не задерживает независимые цели.
5. Подтвердить возвращение выбранного AP: тот же MAC, актуальный Online/RUN и uptime после reboot, если доступен. При наличии разрешения оформить успешную заявку и прочитать сохранённый статус. Для этого сценария существующая форма использует **Resolved Waiting For Confirmation**, не окончательное **Resolved**. Отдельно отметить непроверенную работу портала/клиентского сервиса.
6. Кратко сообщить: какие AP перезагружены, какие статусы заявок сохранены, что заблокировано. Детальный отчёт нужен только для существенного инцидента или по запросу.

## Известные ограничения, подтверждённые 12.10.2026

Это факты о проверенной версии, не вечные запреты. Если код изменён, перечитать только соответствующий участок и обновить запись.

- **Выбор заявок:** число в IP или «Plan change request» может ошибочно стать комнатой. Проверить смысл и ограничить `--ticket-id`.
- **XNet:** при выборе точного account очистить лишние фильтры `deviceMarsha`, public IP, manufacturer/model. Проверить выбранный account и type WLC. Использовать Primary IP, Optional IP и URL в Note; не объявлять WLC отсутствующим по одному пустому результату.
- **Доверие:** исходные browser helpers используют широкие certificate bypass, SSH helper — AutoAddPolicy. Их нельзя запускать для отправки паролей в таком виде. Нужны проверенные host keys / доверенный TLS; подтверждённые в этой операции отпечатки не спрашивать повторно, пока они совпадают. Исправлять именно подключение, не строить новую систему агента. Пароли не передавать в CLI/логи.
- **Соседние комнаты:** в некоторых backends есть nearest-room fallback. При отсутствии точной привязки не применять его молча; явное разрешение пользователя на выбор кандидата достаточно. Зафиксировать выбранный AP и неподтверждённое покрытие.
- **Массовый PoE:** специальная ветка RUMOSUC затрагивает все порты 1–48. Авторизация на отдельный AP не разрешает её; исключить эту ветку из комнатного запуска.
- **Closure:** штатный runner оформляет заявку сразу после возвращения backend, что может означать только отправку команды. Перед разрешённым closure должна быть реальная проверка возвращения AP; неизвестный результат не считать успешным.
- **Ruijie:** после top-level confirmation снова выбрать iframe `/ac/ap/ap-reload.htm` перед чтением таблицы. AP Detail в Monitoring даёт текущие MAC, Online, uptime и RF. Чтение внешней страницы не доказывает отсутствие AP.
- **Ruckus:** uptime бывает полным и коротким (`152 days ...`, `5 mins 6 secs`). `Disabled` в секции Mesh не доказывает общий down. Не посылать controller reboot или команды для всех AP вместо адресного действия.

Одна ошибка → проверка соответствующего участка → точечное исправление/существующий fallback. Если безопасного пути нет, оставить конкретную цель заблокированной, выполнить остальные и назвать необходимый доступ. Не ослаблять проверки доверия и не повторять неопределённые перезагрузки ради скорости.
