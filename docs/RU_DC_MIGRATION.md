# Перевод объекта на RU DC

Эта инструкция описывает работу инженера с Codex и существующей программой ASA / RouterOS. Она обобщает локально использованный порядок переноса. Конфигурации объектов, внутренние адреса, сертификаты и закрытые инструкции сюда не скопированы. Конкретный набор команд определяется текущей топологией и одобренной процедурой объекта.

## 1. Подготовить рабочее место и входные данные

Установите `requirements-operational.txt` в виртуальное окружение из README. Запустите `python -m agent_tools.offline_tests --operational`: тесты используют mocks, сеть и внешние процессы заблокированы.

Получите по внутреннему разрешённому каналу:

| Данные | Что должно быть известно |
|---|---|
| Цель | Точный site, IP, hostname, serial, модель и версия ASA / RouterOS |
| Inventory | Локальный XLSX XNet; первая строка содержит имена полей экспорта |
| Доступ | Локальные реквизиты устройства; разрешённый RADIUS fallback при отказе аутентификации |
| Существующий SSH trust | JSON точных endpoint → SHA256 fingerprint, используемый имеющейся программой |
| RU DC | Одобренные peer, identity, подсети/selectors и параметры IKE/IPsec |
| PKI | Одобренный CA, SCEP URL, имя сертификата, правила выдачи и защищённый challenge |
| Сервисы | Требуемые management / portal / WLC / DNS / DHCP зависимости и тестовые потоки |
| Операция | Окно работ, резервный доступ, критерии отката и локальный журнал |

Runner выбирает **ровно одну** строку XLSX по `ip`. Используемые поля: `ip`, `login`, `password`, `model`, `controlName`, `serialNumber`; для ASA при необходимости `enablePassword`. `--connect-host` / `--connect-port` задают документированный SSH endpoint, не меняя выбранную запись inventory. Для нестандартного порта trust использует `[host]:port`.

Программа не проверяет применимость каждого переданного CLI к модели/прошивке и не заменяет проверку инженером hostname, serial и версии. До изменения сопоставьте фактические значения с выбранной целью; при несовпадении остановитесь.

Inventory и журнал сохраняйте вне Git. В этой инструкции `python` означает Python активированного виртуального окружения; иначе используйте полный путь к нему из README.

## 2. Сначала определить фактический статус

Прочитайте последний журнал объекта и текущее состояние. Исторический план может содержать уже выполненные этапы. Не повторяйте переключение, enrollment, перенос адреса или изменение NAT только потому, что они перечислены в старом плане.

Выполните локальный поиск KB до подготовки конфигурационных рекомендаций:

```powershell
python agent_tools/kb_search.py "SCEP" --db <local-knowledge.db> --top 6 --metadata-only
python agent_tools/kb_search.py "CCR" --db <local-knowledge.db> --top 6 --metadata-only
```

В приватном журнале укажите ID документа, URL/путь, дату документа и дату снимка **2026-10-08**. Например, локальный поиск находит `wiki:0128`, `wiki/0128-CCR-hardware-Mikrotik---acting-as-Gateway-and-Firewall---LACP.md`, дата документа в KB `2026-10-08`. Применимость надо проверить по актуальной топологии; отсутствие KB не заменяет её содержимое догадками.

Пример чтения идентичности RouterOS, после подстановки локальных путей:

```powershell
python tools/ru_dc_vpn.py read --inventory <export.xlsx> --host <inventory-IP> --trust <existing-trust.json> --output-dir <private-operation-dir> --label 01_identity --command "/system identity print" --command "/system routerboard print" --command "/system resource print"
```

Для ASA используйте подходящие её версии `show hostname`, `show version`, `show inventory`, `show failover`, `show clock`. Режим `read` передаёт команды как есть: выбирайте только проверенные команды чтения. Это операционная утилита с полномочиями своей SSH-учётной записи, а не sandbox или typed API.

Снимите относящиеся к операции интерфейсы/VLAN/bridge/VRRP, адреса, маршруты в обе стороны, NAT и ACL/filter с порядком правил, IKE/IPsec и сертификаты. Сопоставьте путь ASA → RouterOS → RU DC и обратный путь. Отдельно зафиксируйте management, WLC/OLT и portal зависимости, если они есть на объекте. Не переносите в отчёт секретные строки или полный key material.

## 3. Подготовить план и откат

Разделите план на этапы: исходное состояние и резервная копия; PKI; подготовка VPN; проверка нового пути; переключение только выбранных сетей/сервисов; итоговая проверка. Для каждого этапа запишите точные команды под проверенную версию, ожидаемый результат, обратные команды и условие остановки.

Определите, где будет gateway/VIP после переноса, какой узел сейчас master, какие selectors нужны с обеих сторон и где применяется NAT. Проверьте отсутствие дублирующихся адресов и конфликтующих старых политик. План должен учитывать сохранение пути управления и независимый способ восстановления. Согласуйте конкретные изменения и окно работ с владельцем операции; полученное разрешение повторно не спрашивайте.

RouterOS export через существующий runner:

```powershell
python tools/ru_dc_vpn.py backup --inventory <export.xlsx> --host <inventory-IP> --trust <existing-trust.json> --output-dir <private-operation-dir> --label 02_before
```

Этот режим создаёт `.rsc` на устройстве и скачивает его по SFTP; это файловая операция на устройстве, не чистое чтение. Для ASA подготовьте резервную копию отдельно по одобренной процедуре. Конфиги и backup остаются приватными.

## 4. Сертификат и SCEP

Перед enrollment проверьте время устройства, доступность одобренного сервиса, CA и действующие сертификаты. Не удаляйте существующие hotspot-сертификаты. Адрес сервиса и криптографические параметры берите из актуальной одобренной процедуры.

Файл команд должен содержать единственный маркер `{{SCEP_CHALLENGE}}` вместо значения challenge. Передайте его через `--prompt-scep-challenge`: подстановка выполняется в памяти, значение не записывается в файл команд. При автоматизированном Windows PTY используйте `--prompt-input-encoding hex`; hex остаётся секретом и передаётся только в скрытый stdin. Человек в обычном терминале использует режим `plain` по умолчанию.

```powershell
python tools/ru_dc_vpn.py file --inventory <export.xlsx> --host <inventory-IP> --trust <existing-trust.json> --output-dir <private-operation-dir> --label 03_enrollment --path <reviewed-enrollment.txt> --prompt-scep-challenge
```

SCEP enrollment не считается завершённым по факту отправки запроса. Прочитайте итоговое состояние сертификата, проверьте ключ, назначение, issuer, цепочку и сроки. Промежуточный статус ошибки требует проверки результата существующего запроса до повторной отправки. Жизненный цикл SCEP описан в [официальной документации MikroTik Certificates](https://help.mikrotik.com/docs/spaces/ROS/pages/2555969/Certificates).

По умолчанию вход использует XNet → разрешённый RADIUS только после отказа аутентификации. Timeout, ошибка транспорта/ключа, MFA и недостаточные права не повод пробовать другую учётку. RADIUS берётся из Credential Manager или ссылок на environment в `config/network_diagnostics.json`; значений паролей там нет. Явно разрешённое исключение user-first: `--username <account> --prompt-password --user-first`; для согласованного восстановления доступны `--user-keyboard-interactive` и `--no-inventory-fallback`.

## 5. VPN и переключение

Подготовленные команды выполняются отдельно, только после проверки точной цели и разрешения на этот этап:

```powershell
python tools/ru_dc_vpn.py file --inventory <export.xlsx> --host <inventory-IP> --trust <existing-trust.json> --output-dir <private-operation-dir> --label 04_vpn_prepare --path <reviewed-vpn-commands.txt>
```

Одна непустая строка файла — одна команда; строки, начинающиеся с `#`, пропускаются. Для RouterOS сложный скрипт должен быть одной корректной строкой, проверенной под выбранную версию. В режиме `file` распознанная ошибка CLI останавливает следующие команды. При timeout или разрыве соединения результат уже отправленной команды может быть неизвестен: сначала прочитайте состояние, не отправляйте изменение повторно.

Несовпадение peer identity и сертификата требует проверки ожидаемого identity и цепочки. Широкое отключение проверки peer не является исправлением. Если одобренная процедура использует `match-by=certificate`, точный `remote-certificate` должен быть независимо проверен. Параметры описаны в [официальной документации MikroTik IPsec](https://help.mikrotik.com/docs/spaces/ROS/pages/11993097/IPsec).

Для уже имеющегося ограниченного журнала режим `peer-certificate --log-prefix <PREFIX> --expected-peer-cn <approved-CN> --ca <approved-root.crt>` с обычными параметрами inventory/host/trust/output/label извлекает публичные X.509 CERT payload и проверяет подписи/сроки цепочки до сохранения публичного leaf. Он не включает debug, не меняет trust или конфигурацию и не устанавливает доверие только на основании данных peer. Если сертификата/цепочки в журнале нет — режим останавливается. Обновление привязки при ротации сертификата — отдельное проверенное изменение.

Переключайте только согласованные management/VLAN/route/NAT/portal зависимости. Не добавляйте по ходу миграции firmware upgrade, очистку конфигурации или изменения посторонних сетей.

## 6. Проверить сервис и принять результат

Для каждого ожидаемого selector подтвердите IKE/Phase 2 и передачу пакетов в обе стороны по счётчикам при тестовом трафике. Проверьте маршрут туда и обратно, NAT/filter, доступ управления с разрешённой стороны и фактический пользовательский сервис. Поднявшийся tunnel сам по себе не доказывает работоспособность portal, DNS/DHCP или доступа гостей.

Если затронуты HA/VRRP, проверьте актуальные роли, VIP и согласованность участников. Проверку отказоустойчивости проводите только в отдельно согласованном объёме; наличие master не подтверждает полный HA-тест. Не объявляйте недоступный или не проверенный узел исправным.

В едином журнале сохраните: цель, этап и время, команду/действие без секретов, результат и доказательства, неизвестные результаты, выполненный откат и итоговую проверку. Не выполняйте save автоматически; RouterOS сохраняет многие изменения сразу, поэтому откат должен быть готов до применения. Для ASA запись startup-config требует соответствующего разрешения.

Откат выполняется по подготовленному плану при потере управления, нарушении согласованного сервиса или невыполнении критериев приёмки. Сначала установите текущее состояние и объём уже выполненных изменений. Повторное исполнение всего плана или всего rollback вслепую запрещено.

## Запрос для нового инженера

> Используй mikenopa-network и network-diagnostics. Нужно перевести выбранный объект на RU DC по docs/RU_DC_MIGRATION.md. Inventory, существующий trust-файл, одобренные параметры RU DC и приватный каталог операции указаны локально. Прочитай последний статус, определи, что уже сделано, проверь точную цель и версию. Подготовь минимальный поэтапный план и откат с проверкой обоих направлений VPN и реальных сервисов. Используй tools/ru_dc_vpn.py; не создавай новый SSH-исполнитель и не подключай его к offline agent API. Не повторяй изменения с неизвестным результатом.
